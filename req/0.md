# 2. People / User Management

The current People module allows adding users, but there is no concept of application login or authentication.

This entire module needs to be redesigned around proper user management.

---

## Authentication

Each user should have login credentials.

### Password Policy

* Minimum 8 characters
* Alphanumeric password
* Password expiry after 30 days
* User must change password before continuing
* Previous 3 passwords cannot be reused

### Suggested Database Design

Create a separate table:

```
user_password_history
```

Example structure:

* id
* user_id
* password_hash
* level

Where:

* Level 0 = Current Password
* Level 1 = Previous Password
* Level 2 = Second Previous Password

This makes password history enforcement straightforward.

---

## User Levels

There will be three user levels.

### A. Super Admin

When a new user clicks **Create Account**, they become the Super Admin of a new organization.

During organization creation:

Required fields:

* Organization Name
* GST Number

The GST Number must be globally unique so that duplicate organizations cannot be created.

Suggested Organization table:

```
Organization

id
name
gst_number (Unique)
super_admin_user_id
```

A Super Admin should also be able to create additional organizations.

Each organization must still have a unique GST Number.

---

### B. Admin

An Admin belongs to exactly one organization.

They have full administrative rights within that organization, including:

* User Management
* Policy Management
* Evidence Management
* Controls
* Registers
* Audits
* Tasks
* Reports

Think of this role as the Compliance Department Head.

---

### C. User

Regular users only see what they have permission to access.

Permissions should be Role-Based.

Example:

If a user only has permission for:

* Policies

  * View
  * Add
  * Edit

Then only those menus and actions should be visible.

No access should exist outside their assigned permissions.

---

## Role & Permission System

Instead of hardcoding permissions, implement a Role-Based Access Control (RBAC) system.

When creating a Role:

Allow selecting permissions using checkboxes.

Example:

Policies

* View
* Add
* Edit
* Delete

Audits

* View
* Add
* Edit
* Delete

Controls

* View
* Add
* Edit
* Delete

...and so on.

Users are assigned Roles.

Roles define menu visibility and API permissions.

# 3. Audits

The Excel import feature works well, but several important capabilities are missing.

## A. Manual Control Reassignment

During Excel import, controls are automatically mapped using AI or confidence matching.

Currently, there is no way to manually change the assigned Control afterward.

Need:

* Reassign Control
* Search Control
* Replace Control Mapping

---

## B. File Preview

Currently uploaded files cannot be previewed.

Need generic preview support for:

* PDF
* DOC/DOCX
* XLS/XLSX
* Images

A reusable file preview component should be used throughout the application.

---

## C. Better Audit Point Details

When opening an Audit Point, it currently shows something like:

```
GRP 5.a
```

It should also display the linked Master Control description.

A tooltip, hover card, or expandable section would work well.

---

## D. Export Improvements

While exporting Excel,

the Evidence column should contain:

* Evidence Name
* Download Link (or reference)

instead of being empty.

---

# 4. Controls

The Controls module is intended to be the master library of controls across multiple compliance frameworks and domains.

These controls will later be linked manually or automatically (using AI) to Audit Points.

---

## Required Improvements

### Add Control

Allow users to manually create new Controls.

Current functionality is missing.

---

### Better Slide-out Panel

The right-side panel needs improvement.

Increase its width and display:

* Linked Audit Points
* Linked Evidence
* Linked Policies
* Attachments

with better readability.

---

### Evidence & Policy at Control Level

A Control should support attaching:

* Evidence
* Policies

When a Control is linked to an Audit Point,

those attachments should automatically appear in the Audit.

However, the UI should clearly distinguish between:

* Attached through Control
* Attached directly to Audit Point

---

### Cross Navigation

Users should be able to jump between linked records.

Example:

Inside Control

Mapped Audit Point

↓

Click

↓

Open Audit Point page

Likewise,

Audit Point

↓

Click Control

↓

Open Control

Routing should be standardized.

Example:

```
/controls/view/:id

/audits/view/:id

/evidence/view/:id
```

---

# 5. Registers

Currently everything exists under one Registers menu.

Although functional, these should eventually become independent modules.

Modules include:

* Risks
* Assets
* Data Inventory
* Third Parties
* Incidents

Hide the Obligations module for now.

It will be revisited later.

---

## Risks

Need improvements:

* Category should be a dropdown
* File attachments
* Evidence
* Who reported it
* Who reviewed it
* Linked Controls

Manual text entry for Category should be avoided to prevent spelling inconsistencies.

---

## Assets

Assets should become type-aware.

Example:

### Physical Asset

Fields:

* Model
* Serial Number
* Manufacturer
* Photo
* Location

### Virtual Asset

Fields may include:

* IP Address
* Hostname
* Cloud Provider
* VM
* Docker Container
* Subscription
* Service URL

Virtual assets may not require photographs.

---

## Data Inventory

Classification already exists.

Need additional fields:

* Data Type
* Database
* S3 Storage
* Application
* API
* File Server
* Cloud Storage

The inventory should support multiple storage types.

---

## Third Parties

Currently Category is free text.

Convert it into a dropdown.

The overall purpose and workflow of this module still needs discussion before expanding it further.

---

## Incidents

Should become a complete incident management system.

Include:

* Description
* Root Cause
* Evidence
* Images
* PDFs
* Timeline
* Resolution
* Review Notes
* User Comments
* Corrective Actions

Example:

Database container crashed

↓

Evidence

↓

Investigation

↓

Resolution

↓

Preventive Action

Current edit page is a reasonable starting point but requires expansion.

* Procedures

* Google Docs

Need support for:

* Formatting
* Tables
* Images
* Lists
* Headings
* Comments (future)

---

## Export

Support exporting as:

* DOCX
* PDF

---

## Version Management

This module needs proper planning before implementation.

It should include:

* Draft
* Review
* Approval
* Published
* Archived

Version history should be maintained.

This is likely one of the largest modules in the application and should be designed carefully before implementation.

---

# 7. Evidence Library

This should become the central repository for uploaded files.

Workflow:

Bulk Upload

↓

Rename Evidence

↓

Edit Metadata

↓

Set Valid Until Date

↓

Assign to Controls

↓

Automatically available wherever those Controls are linked.

The default Evidence Name should be the uploaded filename, but users should be able to rename it.

---

# 8. Tasks

Tasks should become the scheduling engine of the platform.

Examples:

* Policy renewal reminders
* Quarterly table cleaning
* Annual reviews
* Compliance activities
* Internal audit reminders

Need support for:

* Recurring schedules
* Daily
* Weekly
* Monthly
* Quarterly
* Yearly

Tasks should also support linking to:

* Controls
* Policies
* Risks
* Audits

so that compliance activities remain connected to the underlying framework.
